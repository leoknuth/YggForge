## 目的

本文记录对参考仓库 `agent-profile` 的评估结论，以及本次迁移到 `YggForge` 的取舍标准。

## 总体判断

`agent-profile` 有几个明显优点：

- 把 Agent 协作知识拆成了 `rules / skills / tools / hippocampus`
- 明确提出了“错题本 -> 规则 / 技能晋升”机制
- 对全局配置的部署、回收、脱敏、git 更新形成了闭环
- 在一些工程细节上已经积累出可复用结论，尤其是 C++ 风格、git 操作、路径表达和注释边界

但它也有明显问题：

- 结构强绑定 Cursor
- 规则以扁平 `.mdc` 文件堆叠为主，规模增大后检索成本会明显上升
- 稳定规则、一次性纠错、执行步骤、工具细节混得较近
- 一些规则写的是“如何在 Cursor 中执行”，不适合作为跨 Agent 的知识真源

## 迁移原则

本次迁移遵循以下原则：

1. 迁移“稳定知识”，不迁移“工具偶然性”。
2. 迁移“原则与结构”，不原样复制 Cursor 目录形态。
3. 迁移后要能被 Cursor、OpenCode、Codex 共同消费。
4. 执行步骤收敛到文档或脚本入口，避免规则文件重复描述细节。
5. 错题与经验先进入 `lessons/`，只有长期稳定后才进入 `rules/`。

## 本次吸收的核心内容

### 1. 纠错与长期记忆

吸收了 `correction-notebook` 和 `learned-mistakes.md` 的核心思路：

- 用户的原则性纠正要能持久化
- 错题本不只是记错，还要记录场景、错误、纠正、沉淀后的规则
- 当一条经验稳定复现后，应允许晋升为规则或模板

### 2. 路径表达边界

吸收了“聊天回复中可以展开绝对路径，但持久化文档中不默认写死机器路径”的原则。

### 3. Git 操作纪律

吸收了这些稳定约束：

- `git add -> git commit -> git push -> git status` 必须串行
- “无差异”结论必须基于实际命令结果
- `git status` 更适合作为内部核验，而非默认对话输出
- 提交回报应以高信息密度摘要为主

### 4. 注释与来源边界

吸收了“代码注释描述当前仓库行为，不在注释中写外部仓库来源”的原则。

### 5. C++ 风格细节

吸收了这些可落地结论：

- 中文注释
- `#pragma once`
- `Type* p` / `Type& r`
- 避免 Doxygen 风格文档块与尾随成员注释
- 逻辑段与成员分组注释模板

## 没有直接迁移的内容

以下内容本次没有直接迁移为 `YggForge` 规则真源：

- 强绑定 `~/.cursor` 的目录与路径规则
- 依赖 Cursor 规则触发器的 `.mdc` 组织方式
- 仅适用于 Cursor 全局同步的工具调用习惯
- 特定环境、特定仓库、特定业务的纠错条目

这些内容仍然有参考价值，但更适合作为：

- 设计参考
- 部署实现参考
- 以后做 Cursor 专属 profile 时再吸收

## 迁移后的结构优化

相较于 `agent-profile`，`YggForge` 采用：

- `rules/` 存放稳定约束
- `lessons/` 存放错题、反例、经验
- `decisions/` 存放架构取舍
- `profiles/` 存放工具投影

这样可以避免“规则、流程、工具、记忆”在同一层扁平堆叠。
